## request-1. [medium, wire-mismatch] CONFIRMED: Noul criteria always writes both `true` and `false`; the one-sided shape both SDKs send and live-test is unreachable

- Java: `/Users/jim/src/typesafe-client/typesafe-client/src/main/java/software/sava/typesafe/NoulCriteria.java:13`
- Reference: `/Users/jim/docs/ai/typesafe/typesafe-sdk-js/test/integration/api.integration.ts:91`
- Java does: `writeTo` unconditionally emits `{"true":<json>,"false":<json>}`, writing the JSON literal `null` for whichever side is null (JsonContent.java:32-38). There is no representation for an absent key, and none for an empty `criteria:{}`.
- Reference does: JS `noul(instructions, {true: ...})` stores only the keys given and `JSON.stringify` drops nothing else, so the live integration test posts `"criteria":{"true":{...}}` with no `false` key. Python's `NoulCriteria` is `TypedDict(total=False)` (question_types.py:14-23) and tests/test_questions.py:139-160 pins `{"true": "Yes"}`, `{"false": "No"}` and `{}` as exact wire bodies.
- Consequence: A Java caller describing only the yes side sends `"criteria":{"true":"...","false":null}` where both reference SDKs send `{"true":"..."}`. Under the published schema (NoulCriteria.false defaults to None, _schemas/models.py:87-89) both decode to the same value, but the bytes differ on every one-sided noul, and nothing in the Java suite or the SDKs' suites shows the server treats an explicit null description the same as an omitted one when it renders criteria for the model.
- Refuter's evidence: NoulCriteria.java:13-19 unconditionally appends `{"true":` … `,"false":` … `}`, and JsonContent.write (JsonContent.java:32-38) emits the literal `null` for a null side. The Java suite pins both halves of this: QuestionSerializationTests.java:54-56 pins `{"true":null,"false":"no"}` and :251-253 pins `{"true":"yes","false":null}`. Noul.java:20-23 only omits `criteria` entirely when the record field is null, so the reachable shapes are exactly `criteria` absent or both keys present; `criteria:{}` and one-sided are not expressible. JS: typesafe-sdk-js/test/integration/api.integration.ts:87-93 live-tests `noul(instructions, {true: {...}})` and questions.ts/client.ts:316-318 pass the object straight to JSON.stringify, so only `true` is sent. Python: question_types.py:14-23 is `TypedDict(total=False)` and tests/test_questions.py:139-160 pins `{}`, `{"true":"Yes"}` and `{"false":"No"}` as exact bodies. Schema NoulCriteria (models.py:83-89) defaults both sides to None, so an explicit null and an omitted key decode identically.
- **Corrected proposal:** Give NoulCriteria a per-side omit (skip the key when that description is null) and a way to express `criteria:{}`, and add a QuestionSerializationTests case pinning `{"type":"noul","instructions":"q","criteria":{"true":"yes"}}`. Note when writing it up that the existing tests at QuestionSerializationTests.java:54-56 and :251-253 deliberately pin the two-key form and would need updating, and that under the published schema an explicit null and an omitted key decode to the same NoulCriteria — the divergence is in the bytes and in whatever the server renders to the model, which no suite on either side pins.


## request-2. [medium, wire-mismatch] PARTLY: No Accept, User-Agent, X-TypeSafe-SDK or X-TypeSafe-Runtime header on any request

- Java: `/Users/jim/src/typesafe-client/typesafe-client/src/main/java/software/sava/typesafe/TypeSafeClientImpl.java:88`
- Reference: `/Users/jim/docs/ai/typesafe/typesafe-sdk-python/src/typesafe_sdk/_core/transport.py:111`
- Java does: Requests carry only `Content-Type: application/json` (set by JsonHttpClient.newJsonRequest) and the `Authorization` bearer added by TypeSafeClient.java:132. TypeSafeClientWireTests.java:99-100 asserts exactly those two and nothing more.
- Reference does: Both SDKs set four more headers on every attempt: `Accept: application/json`, `User-Agent: typesafe-sdk/<version>`, `X-TypeSafe-SDK: typesafe-sdk/<version>`, `X-TypeSafe-Runtime: python/... | node/...` — transport.py:111-118, client.ts:353-361 — and pin them in tests/test_clients.py:389-394 and test/release-regressions.test.ts:49-55.
- Consequence: Every Java request is distinguishable at the edge from an SDK request: no Accept (server falls back to `*/*`), no client identification for vendor telemetry, rate-limit classes or support triage. If the API ever content-negotiates or gates on a known client, the Java client is the one that breaks.
- Refuter's evidence: Accept, X-TypeSafe-SDK and X-TypeSafe-Runtime are genuinely absent: the only headers the client sets are Content-Type (JsonHttpClient.newJsonRequest, sava-rpc 25.11.1 sources, JsonHttpClient.java:85-90) and the bearer at TypeSafeClient.java:132. The JDK supplies its own default whenever one is not set, so the accurate claim is 'no SDK-identifying User-Agent', not 'no User-Agent'. The evidence line 'TypeSafeClientWireTests.java:99-100 asserts exactly those two and nothing more' also overstates: those two lines assert Authorization and Content-type are present; nothing in that suite asserts any header is absent. Reference side checks out: transport.py:111-118 sets the four, client.ts:353-357 sets them, pinned at tests/test_clients.py:389-394 and test/release-regressions.test.ts:49-55.
- **Corrected proposal:** Set `Accept: application/json`, `X-TypeSafe-SDK: sava-typesafe-client/<version>` and `X-TypeSafe-Runtime: java/<version>` inside the bearer operator (TypeSafeClient.java:132) so they land before the caller's `extendRequest`, and replace the JDK's default `Java-http-client/<ver>` User-Agent with an SDK-identifying one. Assert all four in TypeSafeClientWireTests, and add the absence assertions the suite currently lacks.

- Reference: `/Users/jim/docs/ai/typesafe/typesafe-sdk-python/src/typesafe_sdk/_schemas/models.py:198`

- Consequence: Forgetting `.state(...)` is not a compile or construction error; it becomes a 422 at runtime, and the javadoc tells the caller it is a supported mode. If the server does reject null state, every such request is wasted.
- Refuter's evidence: The Java behaviour is exactly as described: SystemOneRequest.java:59-60 writes `"state":` then JsonContent.write, which emits `null`; the builder defaults state to null (SystemOneRequest.java:78) and the constructor never checks it; the javadoc at SystemOneRequest.java:17 says 'null evaluates `null`'; QuestionSerializationTests.java:114-118 and :255-257 pin `{"state":null,`. So 'every such request is wasted' is unverified.
- **Corrected proposal:** The divergence is real and the javadoc asserts a mode only one of the two references supports, but do not assert a 422. Either confirm against the live API whether a null state is accepted and then pin a wire test, or reject null in the SystemOneRequest constructor. Until it is confirmed, reword the javadoc at SystemOneRequest.java:17 to say the generated schema (typesafe-sdk-python/src/typesafe_sdk/_schemas/models.py:197-202) marks state required and non-nullable while the JS SDK types and sends null, and that the Java client's behaviour is untested against the server.


## request-6. [low, behaviour-gap] CONFIRMED: extendRequest runs after the bearer header, so a caller can overwrite Authorization and Content-Type

- Java: `/Users/jim/src/typesafe-client/typesafe-client/src/main/java/software/sava/typesafe/TypeSafeClient.java:135`
- Reference: `/Users/jim/docs/ai/typesafe/typesafe-sdk-js/src/client.ts:352`
- Java does: `builder -> extend.apply(bearer.apply(builder))` applies the user's operator last, so `extendRequest(b -> b.setHeader("Authorization", ...))` or `setHeader("Content-Type", "text/plain")` wins and goes out on the wire.
- Reference does: JS merges user headers first with the comment "User-supplied headers go first so they can't clobber auth or the JSON content type" and then overwrites Authorization/Accept/User-Agent/Content-Type; Python does the same at transport.py:108-119. release-regressions.test.ts:15-57 pins that caller-supplied `authorization`, `content-type`, `accept`, `user-agent` in any casing are all replaced.
- Consequence: A helper that adds tracing headers can accidentally strip or downgrade auth or the JSON content type, producing a 401 or a 415 whose cause is invisible in the client; both SDKs make this impossible by construction.
- Refuter's evidence: TypeSafeClient.java:134-136 builds `builder -> extend.apply(bearer.apply(builder))`, so the caller's operator is last; JsonHttpClient.java:197-199 and :223-228 then apply that operator after `newJsonRequest` has set Content-Type. I reproduced it on JDK 25.0.2 with a loopback server using the same chain: a user operator calling `setHeader("Authorization", "Bearer HIJACKED").setHeader("Content-Type", "text/plain")` produced `Authorization=[Bearer HIJACKED], Content-type=[text/plain]` at the server, i.e. the real key never left. TypeSafeClientWireTests.java:118-131 only covers the benign case (an X-Trace header alongside an untouched bearer). JS merges user headers first then overwrites (client.ts:351-359, comment: 'User-supplied headers go first so they can't clobber auth or the JSON content type'), Python the same at transport.py:108-119, both pinned at test/release-regressions.test.ts:15-57 and tests/test_clients.py:380-398.
- **Corrected proposal:** Compose the operator the other way — `builder -> bearer.apply(extend.apply(builder))` at TypeSafeClient.java:134-136 — so Authorization (and, if the header work in finding 2 lands, Accept and the X-TypeSafe-* pair) is set after the caller's extension, and add a wire test asserting that an `extendRequest` that sets Authorization or Content-Type does not reach the server. Cite TypeSafeClient.java:134-136 rather than :135.
